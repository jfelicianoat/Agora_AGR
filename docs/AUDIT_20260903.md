## 2. Defectos encontrados y corregidos

Los cuatro nacen del mismo origen: **los dobles de test hablaban un contrato de AI_Broker
que el broker real no usa**. Cada uno tiene ahora prueba de regresión en
`tests/test_regressions_20260903.py`.

### D1 — La CARD se cerraba con el sobre JSON del broker, no con el entregable (grave)

`_result_bytes` buscaba el texto en `content`, `text`, `output` o `answer`. El broker real
nunca usa ninguna: entrega en `result_markdown` y `assistant_content`
(`AI_Broker/app/coordinator.py:1971-1972` y `:2773-2774`). El código caía al `json.dumps`
de reserva, así que **toda tarjeta del harness broker se cerraba con un volcado JSON
llamado `broker-result.md`**, y el Record lo declaraba «Verified artifact».

Evidencia real (tarea `task_fc6c590ce84547a6ac520834ea1f576d`):

```
result keys: ['assistant_content', 'fallback_used', 'inference_kind', 'model_used',
              'models_used', 'output_format', 'result_markdown', 'usage']
```

Corregido: se extraen las claves reales y, si no hay entregable textual, se falla de forma
visible en vez de fabricar uno.

### D2 — `output.format: json` producía una petición que el broker rechaza

`BrokerPolicy` admitía `output_format="json"` pero `build_broker_request` nunca emitía
`json_schema`, que el broker exige (`AI_Broker/app/schemas.py`,
`TaskOutput.require_schema_for_json`). Comprobado contra el broker real:

```
POST /api/v1/tasks -> 422
{"code": "CONTRACT_VALIDATION_FAILED",
 "msg": "output.json_schema is required when output.format is json"}
```

Corregido: `BrokerPolicy` gana `output_schema`, lo exige para JSON y lo prohíbe fuera de él.

### D3 — El sondeo de enrutado del broker se contaba como trabajo de la tarjeta

AI_Broker lanza invocaciones `shadow_probe` bajo el mismo `task_id` para aprender enrutado
(`AI_Broker/app/shadow_probe.py`). Usan **otro modelo**, no reportan `generation` y llegan a
`completed` (`repository.complete_invocation`, línea 266). Agora las trataba como
invocaciones de la CARD, de modo que:

- `_validate_strict` las validaba contra el `target_model` estricto → `BrokerPolicyViolation`
  espuria en tarjetas correctas;
- `_audit["total_cost_usd"]` facturaba a la tarjeta el coste de la exploración del broker.

Corregido: se excluyen del contrato y su coste se registra aparte en `exploratory_cost_usd`.

*Alcance de la verificación:* confirmado leyendo el código del broker y con las invocaciones
reales observadas (rol `shadow_probe` presente en las dos tareas lanzadas hoy). **No se
reprodujo el fallo en vivo**: en las ejecuciones de hoy el sondeo se quedó en `started` y no
llegó a `completed`, así que la carrera existe en el código pero no se disparó.

### D4 — La API mentía sobre el estado final de la tarjeta

`POST /cards/{f}/yield` contestaba siempre `state: "pending"`. Si el `yield` agotaba
`max_attempts`, la tarjeta acababa realmente en `blocked/`. Peor: esa respuesta falsa se
guardaba en el registro de idempotencia, así que el reintento la repetía. Reproducido con
un test que fallaba contra el código anterior. Corregido derivando el estado del sitio real
donde quedó la CARD.

## 3. Contradicción de fondo: el `X-Admin-Token` **no** es dinámico por arranque

Es el hallazgo más importante de la auditoría y **requiere decisión humana**.

La especificación parte de que «AI_Broker genera una credencial diferente en cada arranque».
El código real no hace eso. `AI_Broker/app/admin_auth.py:65` (`resolve_admin_token`) lo
obtiene, por este orden:

1. la variable de entorno `AI_BROKER_ADMIN_TOKEN` (`broker_config.yaml`, `admin_token_env`);
2. el llavero del sistema operativo: `keyring.get_password("ai-broker", "dashboard_admin_token")`.

Es decir: **una credencial persistente**, no una por arranque. El token que se usó hoy
funciona porque vive en uno de esos dos sitios, no porque el broker lo acabara de generar.

Agora resolvió el problema **inventando** el comportamiento que la especificación daba por
supuesto: `BrokerSupervisor` genera él mismo un `secrets.token_urlsafe(32)` y lo inyecta en
el entorno del broker que **él lanza como proceso hijo**. Eso funciona, pero implica que
Agora tiene que ser el dueño del ciclo de vida de AI_Broker, y choca con el despliegue real:

- el broker se arranca con `AI_Broker/arrancar_ai_broker.bat` (que además aborta si el
  puerto 8765 ya está ocupado) o como servicio Windows
  (`AI_Broker/scripts/install_windows_service.ps1`);
- el broker escucha en `192.168.1.52:8765`, no en el `127.0.0.1` que fija el supervisor;
- **F8 lo rompe del todo**: si Windows arranca AI_Broker solo tras el Wake-on-LAN, el
  supervisor de Agora no puede lanzarlo (puerto ocupado) ni conocer su token.

Alternativas, sin tocar AI_Broker:

| Opción | Qué implica | Riesgo |
|---|---|---|
| **A. Leer el mismo llavero** — `keyring.get_password("ai-broker", "dashboard_admin_token")` en el PC IA, y volver a leerlo (limpiando caché) ante un 401/403 | El runner/gateway deja de lanzar el broker; ambos conviven con el arranque real (.bat, servicio, WoL) | Bajo. Es local, no cruza la red, no cambia el broker. **Recomendada** |
| B. Variable de entorno de máquina compartida | Igual de simple, pero el token queda legible para cualquier proceso del usuario | Medio |
| C. Mantener el supervisor | Agora debe ser el único que arranca el broker; incompatible con servicio Windows y con F8 | Alto |

**Recomendación:** opción A, y reescribir el apartado del token del informe F3 para que
describa el ciclo real en vez del supuesto. No se ha implementado: cambia la arquitectura de
F3 y el enunciado exige parar ante ese tipo de decisión.

## 4. Deuda y huecos detectados (no corregidos)

1. **`model_capacity` es metadato muerto.** Los PROFILE lo declaran (`minimum`, `standard`…)
   pero nada lo lee: no existe `models.yml` ni traducción a requisitos del broker. La
   `BrokerPolicy` es global del runner, así que **todos los perfiles comparten política**.
   La especificación lo pide explícitamente.
2. **Fuga de ficheros en el broker al esperar un adjunto.** `AiRunner._prepare_inputs` sube
   los adjuntos *antes* de reclamar la tarjeta y con `attachment_wait_seconds = 5.0` por
   defecto. Un PDF que tarde más en convertirse devuelve `waiting_attachment` — correcto, no
   incrementa `attempts` — pero **en cada sondeo se vuelve a subir el fichero entero**,
   dejando `file_id` huérfanos indefinidamente. Falta memorizar el `file_id` en el
   checkpoint de la CARD.
3. **Artefactos de tarea del broker ignorados.** El broker expone
   `GET /api/v1/tasks/{id}/artifacts` (capacidad `task_artifacts: true`). Agora solo
   materializa el texto del resultado: lo que produzca `run_code` se pierde.
4. **Sin utillaje de certificados.** `agora-api` exige `--cert`/`--key` pero no hay nada que
   cree la CA privada, emita el certificado, lo renueve ni haga pinning. La especificación
   F2 pedía bootstrap controlado, renovación y almacenamiento seguro de claves.
5. **Nombre de fichero mutilado en el Gateway.** `gateway/app.py` sube al broker un temporal
   llamado `agora-gateway-<aleatorio>-<nombre>`, así que el broker registra ese nombre y no
   el original.
6. **`mypy --strict` nunca ha estado verde** (71 errores). La mayoría son anotaciones
   ausentes y stubs no instalados, pero hay dos incompatibilidades de tipo reales en tests.
7. **El Desktop es de solo lectura.** No permite desbloquear, cancelar ni ver runners,
   costes, scheduler ni histórico — eso es alcance F7, pero conviene tenerlo anotado.
8. **`.venv` del repositorio está roto** (sin `pip` ni `pytest`). Todo se ejecutó con el
   Python 3.14 del sistema.
